# gh-source v2 Behavior Specification

## Purpose
`gh_source` is a Zsh-only loader for shell integrations stored in GitHub repositories.
It clones missing repositories, resolves existing checkouts, performs declared actions, and sources files.

## Design Goals
- Keep the public interface small and declarative.
- Make common source declarations concise.
- Avoid external processes on cached source calls.
- Preserve caller state unless an action explicitly changes it.
- Fail before activation when declared resources are unavailable.
- Support existing regular checkouts and nested worktree containers.
- Never convert or destructively repair repositories.
- Expose only the `gh_source` public function.

## Runtime Requirements
- The caller must run Zsh.
- `gh` is required only when cloning a missing repository.
- `git` is required only for `--update`.
- Existing repository validation uses Zsh builtins and filesystem reads.

## Public Interface
```zsh
gh_source owner/repository[/source-file] \
  [--source source-file]... \
  [--path directory]... \
  [--fpath directory]... \
  [--preserve-zsh-options] \
  [--skip-build-if-present value]... \
  [--build command argv...]
```
```zsh
gh_source --loaded owner/repository[/source-file]
gh_source --list
gh_source --update
gh_source --help
```
No aliases for `gh_source` are defined.
Unknown commands and actions fail with a nonzero status.
`--build` is final and consumes every remaining argument.

## Repository Specification
A repository specification starts with `owner/repository`.
An optional remaining path is shorthand for one `--source` action.
```zsh
gh_source owner/repository/plugin.zsh
```
This is equivalent to:
```zsh
gh_source owner/repository --source plugin.zsh
```
The owner and repository segments must be nonempty.
The owner and repository segments may not equal `.` or `..`.
Resource paths must be relative.
Resource paths may not contain empty segments or `..` segments.
`.` segments are removed during normalization.
A resource path containing only `.` resolves to the checkout root.

## Repository Storage
`GH_SOURCE_ROOT` controls the repository storage directory.
Its default value is `$HOME/Github`.
A repository uses the flat storage path `$GH_SOURCE_ROOT/<repository>`.
The owner is validated against Git metadata but is not part of the storage path.

## Missing Repositories
When the storage path does not exist, gh-source clones a normal checkout.
The clone command is equivalent to:
```zsh
gh repo clone owner/repository "$GH_SOURCE_ROOT/repository"
```
Clone failure returns nonzero and stops activation.
An incomplete destination created by the failed clone is removed.
A reported successful clone must produce a `.git` file or directory.
gh-source never creates a bare repository or worktree layout.

## Existing Checkout Resolution
A storage path containing `.git` is the first candidate.
A storage path containing `.bare/HEAD` is treated as a worktree container.
The branch in `.bare/HEAD` selects the primary worktree name.
Only the final branch component is used as the worktree directory name.
If the primary worktree cannot be derived, `main` is tried.
If the derived worktree is not `main`, `main` is also a final fallback.
A worktree candidate must contain a `.git` file or directory.
gh-source never scans arbitrary worktree directories.

## Origin Validation
Every selected checkout must match the requested `owner/repository` identity.
Regular `.git/config` files are supported.
Linked-worktree `.git`, `commondir`, and shared config files are supported.
HTTPS GitHub origins are supported.
SCP-style `git@github.com:owner/repository` origins are supported.
The optional `.git` URL suffix is ignored.
Identity comparison is case-insensitive.
A missing, unsupported, or mismatched origin fails activation.

## Checkout Selection
One checkout candidate must satisfy every declared resource.
Every `--source` path must be a readable regular file.
Every `--path` directory must exist.
Every `--fpath` directory must exist.
The regular checkout is considered before worktree candidates.
Resources may not be combined from different candidates.
Build predicates are not used to choose a checkout.

## Conventional Source Discovery
Discovery runs only when no source, path, fpath, or build action is declared.
1. `<repository>.plugin.zsh`
2. `<repository>.zsh`
3. `init.zsh`
Filename priority takes precedence over checkout priority.
For each filename, the regular checkout is checked before worktree candidates.
Discovery checks only the checkout root.
Subdirectory sources require an explicit path.
Failure reports the attempted conventional filenames.

## Activation Order
1. Evaluate build predicates.
2. Run and verify the build when needed.
3. Apply PATH and fpath actions.
4. Source pending files in declaration order.
5. Register the successful activation.
Build failure prevents all shell mutations.
Missing declared resources prevent all shell mutations.
Runtime effects from a source that has started cannot be rolled back.

## Source Actions
`--source <file>` may be repeated.
The shorthand source is ordered before explicit `--source` actions.
Equivalent normalized source specifications are deduplicated per invocation.
Each source receives an empty positional argument list.
Functions, widgets, aliases, bindings, and global assignments persist.
Plain `typeset` remains function-local under standard Zsh semantics.
Source files see caller options unless preservation is requested.
Option changes from ordinary sources may persist.
The caller's working directory is restored after every source result.
The first nonzero source status stops later sources and is returned.
Names beginning with `_ghs_` are reserved for loader internals during sourcing.

## Zsh Option Preservation
`--preserve-zsh-options` applies to all sources in one invocation.
Protected sources share one local option scope.
An option change from an earlier protected source is visible to later protected sources.
The caller's original options are restored when the source group returns.
Restoration occurs after success and failure.
The special `$options` parameter is hidden from protected sources.
This prevents scripts such as fzf from restoring immutable `zle` state.
A sourced `emulate` command may disable `LOCAL_OPTIONS`.
gh-source re-enables `LOCAL_OPTIONS` before returning so restoration still occurs.
Ordinary source calls do not load or enumerate the options parameter.

## PATH Actions
`--path <directory>` may be repeated.
Resolved directories are appended to the Zsh `path` array.
The tied `PATH` value updates automatically.
Zsh uniqueness is enabled for `path` after a path action.
The first occurrence of each directory is preserved.
Calls without path or fpath actions do not rewrite either array.

## fpath Actions
`--fpath <directory>` may be repeated.
Declared directories are prepended to `fpath` in declaration order.
Zsh uniqueness is enabled for `fpath` after an fpath action.
The first occurrence of each directory is preserved.
The completion directory shipped with gh-source is added once during initialization.

## Conditional Builds
`--build` requires at least one `--skip-build-if-present` predicate.
A predicate first checks for a regular file at `$checkout/<value>`.
If no checkout-relative file exists, the same value is passed to `command -v`.
Predicate values are not split, normalized, or interpreted by type.
The build is skipped when any predicate succeeds.
When every predicate fails, build argv runs directly without evaluation.
The build runs in a subshell rooted at the selected checkout.
The build receives `GH_SOURCE_DIR` with the selected checkout path.
The build receives `GH_SOURCE_REPO` with `owner/repository`.
The build receives `GH_SOURCE_REPO_NAME` with `repository`.
A nonzero build status stops activation and is returned.
After a successful build, all predicates are evaluated again.
At least one predicate must succeed after the build.
Build freshness is defined only by the caller's predicates.
Builds never run during `--update`.

## Activation State
State exists only for the current shell process.
Sources are keyed by normalized `owner/repository/source-file` specifications.
Repositories are keyed by normalized `owner/repository` identities.
Successful source specifications map to their resolved source paths.
Successful repositories map to their selected checkout roots.
Registration occurs only after every declared action succeeds.
Each normalized source specification loads at most once per shell.
Different source specifications remain independent logical loads.
A lone already-loaded source shorthand returns through the cached fast path.
The cached fast path performs no Git, gh, build, option, or source work.

## Management Commands
`gh_source --loaded owner/repository` succeeds after repository activation.
`gh_source --loaded owner/repository/file` succeeds after that source activates.
Invalid or inactive queries return nonzero without activation.
`gh_source --list` prints successful source specifications.
List output follows first-load order and contains one specification per line.
Path-only and fpath-only activations do not add a source-list entry.
Management commands reject extra arguments.

## Repository Updates
`gh_source --update` considers repositories activated in the current shell.
Resolved checkout roots are deduplicated before update.
Each root is checked with `git status --porcelain --untracked-files=normal`.
Tracked or untracked changes cause that root to be refused.
Clean roots update with `git -C <checkout> pull --ff-only`.
Update progress and failures are written to stderr.
Independent repositories continue after one failure.
The final status is nonzero when any repository fails or is dirty.
Updates never reset, clean, stash, checkout, or discard changes.

## Output And Errors
Successful cached activation is silent.
Requested data from `--list` and `--help` is written to stdout.
Clone, build, update, and error output is written to stderr.
Error messages identify the failing repository, checkout, resource, or action.
All failures return a nonzero status.
No failure is registered as a successful activation.

## Performance Contract
Ordinary existing-repository activation uses Zsh builtins and filesystem reads.
Origin validation does not spawn Git.
Validated origins are reused within the shell.
Already-loaded source shorthand calls use only parsing and map lookup.
Option machinery is loaded only for `--preserve-zsh-options`.
External processes are limited to missing clones, requested builds, and updates.

## Examples
```zsh
gh_source hlissner/zsh-autopair/autopair.zsh
```
```zsh
gh_source junegunn/fzf/shell/completion.zsh \
  --path bin \
  --preserve-zsh-options \
  --source shell/key-bindings.zsh
```
```zsh
gh_source perlpunk/shell-completions --fpath zsh
```
```zsh
gh_source Yarden-zamir/navgator/scripts/navgator.zsh \
  --skip-build-if-present navgator \
  --skip-build-if-present target/release/navgator \
  --build cargo build --release
```
